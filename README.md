# Учёт заказов фабрики

Веб-приложение на Next.js (App Router) + Supabase для учёта клиентов, товаров и заказов производства.

## Экраны

- `/login` — вход (доступ ко всем остальным экранам требует авторизации)
- `/clients` — список и добавление клиентов (только CEO)
- `/products` («Склад») — сначала список товаров по названию (без повторов, с бейджем «нехватка» у товаров, где хоть один вариант на нуле или мало), клик открывает карточку товара со всеми его вариантами (цвет/размер/печать) и остатками. Разделён на «Готовую продукцию» и «Склад сырья», остатки видят обе роли, цена и управление каталогом — только CEO
- `/orders/new` — создание заказа (только CEO): поиск/быстрое добавление клиента и поиск товара с выбором варианта прямо в форме
- `/warehouse/order` («Заказ», только Кладовщик) — тот же `OrderForm`, что и `/orders/new` (общий компонент `components/OrderForm.tsx`), с переключателем в конце формы: «Забирает сейчас» (заказ сразу получает статус «Выдан», остаток списывается немедленно) или «Оставить на потом» (статус «Новый», списание — позже при смене статуса)
- `/warehouse/receiving` («Приход», CEO и Кладовщик) — поступление товара на склад с логом (кто привёз, сколько, когда); поддерживает и добавление одного варианта, и пакетное добавление сразу нескольких размеров/цветов через сетку
- `/warehouse/receiving-history` — полная история приходов (только CEO)
- `/warehouse/history` («История», CEO и Кладовщик) — список заказов со статусом «Выдан» (дата выдачи + имя клиента), клик открывает `/orders/[id]`
- `/orders` — список заказов со статусами: новый, подтверждён, в производстве, выдан, отгружен, оплачен, отменён
- `/orders/[id]` — детали заказа и смена статуса (кладовщик тоже может менять статус)
- `/analytics` — аналитика (только CEO)

## Мобильная версия

Приложение рассчитано в первую очередь на использование с телефона.
На ширинах экрана ниже `sm` (640px, т.е. все обычные смартфоны)
боковое меню (`components/Sidebar.tsx`) скрывается и заменяется на
верхний хедер с аккаунтом (`components/MobileHeader.tsx`) и нижнее
меню вкладок (`components/MobileBottomNav.tsx`) — пункты меню
фильтруются по роли так же, как в десктопном сайдбаре
(`components/navItems.tsx` — общий источник пунктов для обоих). Все
таблицы (заказы, склад, клиенты) на мобильном превращаются в список
карточек вместо горизонтальной прокрутки; поля ввода и кнопки
увеличены под палец и используют `text-base` (16px), чтобы избежать
автоматического зума при фокусе на iOS.

## Запуск локально

1. Установите Node.js 18+ (https://nodejs.org).
2. Установите зависимости:

   ```bash
   npm install
   ```

3. Создайте проект на https://supabase.com, откройте **SQL Editor** и выполните файл `supabase/schema.sql` целиком, затем выполните шаги из раздела «Безопасность» ниже (создать пользователя, отключить публичную регистрацию) — без этого войти в приложение будет некому.
4. Скопируйте `.env.local.example` в `.env.local` и вставьте URL и anon key вашего проекта Supabase (**Project Settings → API**):

   ```bash
   cp .env.local.example .env.local
   ```

5. Запустите dev-сервер:

   ```bash
   npm run dev
   ```

6. Откройте http://localhost:3000

## Безопасность

Приложение защищено входом через Supabase Auth: все экраны, кроме `/login`,
требуют авторизации (см. `components/AuthGuard.tsx`), а RLS-политики в
`supabase/schema.sql` разрешают чтение/запись только строкам с
`auth.role() = 'authenticated'`. Это критично, потому что anon-ключ
(`NEXT_PUBLIC_SUPABASE_ANON_KEY`) виден в исходном коде браузера любому
посетителю сайта — без ограничения на уровне БД он мог бы напрямую, в
обход приложения, читать и удалять все данные через Supabase REST API.

### Обязательные шаги при первом деплое / после обновления

1. В Supabase Dashboard создайте хотя бы одного пользователя:
   **Authentication → Users → Add user**.
2. Отключите публичную регистрацию, иначе кто угодно с anon-ключом сможет
   сам себе завести аккаунт через `auth.signUp()` и обойти защиту:
   **Authentication → Providers → Email → «Allow new users to sign up»** → выключить.
3. Для уже развёрнутого проекта выполните по порядку в SQL Editor
   **после** пункта 1: `002_require_auth.sql`, `003_roles_and_stock.sql`,
   `004_fix_view_anon_access.sql`, `005_product_variants.sql`,
   `006_receiving_and_print.sql`, `007_warehouse_type_and_grid.sql`,
   `008_issued_at.sql`.
4. Для нового проекта выполните `supabase/schema.sql`, затем по порядку
   `002_require_auth.sql`, `003_roles_and_stock.sql`,
   `004_fix_view_anon_access.sql`, `005_product_variants.sql`,
   `006_receiving_and_print.sql`, `007_warehouse_type_and_grid.sql`,
   `008_issued_at.sql`.

⚠️ `004_fix_view_anon_access.sql` закрывает утечку: без него
`products_view`/`orders_view`/`order_items_view` были доступны без
входа в систему (Supabase автоматически выдаёт новым объектам схемы
доступ для анонимной роли) — маскировка цены работала, но имена
клиентов, адреса, статусы заказов и остатки склада были видны любому
в интернете, у кого есть публичный anon-ключ. Если вы уже применяли
`003_roles_and_stock.sql` раньше без `004`, выполните `004` как можно
скорее.

### Переменные окружения

`NEXT_PUBLIC_SUPABASE_URL` и `NEXT_PUBLIC_SUPABASE_ANON_KEY` — это
публичный (anon/publishable) ключ, он специально предназначен для
использования в браузере, и раскрытие в бандле — не утечка. Настоящая
защита данных — только RLS-политики выше. На хостинге
(DigitalOcean App Platform → Settings → App-Level Environment Variables)
задавайте оба значения там же, а не коммитьте `.env.local` в git —
он и так в `.gitignore`. Никогда не используйте и не публикуйте
`service_role` ключ Supabase — он обходит RLS полностью и не должен
попадать ни в код, ни в переменные с префиксом `NEXT_PUBLIC_`.

### HTTP-заголовки

`next.config.mjs` отключает заголовок `X-Powered-By` и добавляет
`X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`,
`Permissions-Policy` и `Strict-Transport-Security`. Content-Security-Policy
не добавлен — для App Router его нужно внедрять через nonce в middleware,
это требует отдельного тестирования, чтобы не сломать hydration.

## Роли

Две роли, хранятся в таблице `profiles` (одна строка на пользователя,
привязана к `auth.users` по `id`, есть только у CEO — обычный
пользователь не может сам прочитать чужую строку и не может изменить
свою через API, роль назначается только вручную SQL-запросом):

- **CEO** — полный доступ ко всем разделам без ограничений.
- **Кладовщик** — работает через складскую терминологию: «Приход»,
  «Заказ», «Склад», «История» (раздел «Заказы» из меню убран — заказы,
  оформленные через «Заказ», всё равно видны CEO в «Заказах» и в
  аналитике, менять статус существующих заказов из общего списка
  кладовщик больше не может через навигацию, хотя доступ на уровне API
  не отзывается). Не
  видит цены и суммы нигде, не видит аналитику и не имеет доступа к
  разделу «Клиенты» — при создании заказа может только искать
  существующих клиентов по имени/телефону или добавить нового, указав
  имя и телефон (без email/адреса и без истории его заказов). Все
  ограничения — не только в интерфейсе (пункты меню скрыты), но и на
  уровне базы: прямой запрос к Supabase REST API с тем же anon-ключом
  вернёт отказ в доступе для клиентов и `null` вместо цены для
  заказов/товаров.

Как это устроено технически (см. `supabase/003_roles_and_stock.sql` и
`supabase/005_product_variants.sql`): таблица `clients` защищена
обычной row-policy («вся строка или ничего» для CEO). Для `products`,
`product_variants`, `orders`/`order_items` и точечного поиска клиентов,
где нужно скрыть только отдельные колонки (цену, email/адрес), а не
всю строку, RLS так не умеет — пришлось сделать
`product_variants_view` / `orders_view` / `order_items_view` /
`clients_view`: чувствительная колонка в них — `case when роль = 'ceo'
then значение else null end`, а запись идёт через `INSTEAD OF`
триггеры, которые дополнительно проверяют роль в коде (кладовщику
разрешено менять только `stock_quantity` у варианта товара и `status`
у заказа; создавать заказы и клиентов — обеим ролям, но клиента
кладовщик может создать только с именем и телефоном). Приложение везде
обращается к этим `*_view`, а не к исходным таблицам напрямую.

## Товары и варианты

Товар (`products`: название + цена — одна цена на все его варианты)
может существовать в нескольких вариантах (`product_variants`: цвет,
размер, артикул, ед. изм., остаток — у каждого варианта свой
`stock_quantity`). При добавлении варианта название товара ищется без
учёта регистра: совпало — вариант добавляется к существующему товару,
не совпало — создаётся новый товар. Переименовать товар задним числом
(что затронуло бы все его варианты) через интерфейс нельзя — только
через новый вариант.

Остаток подсвечивается: `0` — красным «Нет в наличии», `1–30` —
жёлтым «Мало (N)» (порог задан константой `LOW_STOCK_THRESHOLD` в
`lib/types.ts`), выше — обычным цветом. Подсветка используется как на
складе, так и при подборе товара в форме заказа.

Третий параметр варианта — печать (`print_type`, по умолчанию «без
печати»). В отличие от цвета/размера это поле `not null` — если бы оно
могло быть `NULL`, как цвет/размер, уникальность варианта (цвет+размер+
печать) не работала бы: в Postgres два `NULL` в уникальном ограничении
не считаются дубликатом друг друга.

## Приход, Заказ и История

Кладовщик работает через складские действия вместо общей формы заказа
(нижнее меню: Приход · Заказ · Склад · История):

- **Приход** (`/warehouse/receiving`, доступен и CEO) — фиксирует
  поступление товара: выбор существующего варианта (или создание
  нового товара — только название и код, без цены) + количество
  (пачки × штук в пачке, вводится каждый раз заново — не хранится как
  настройка товара — плюс штуки россыпню) + кто привёз + комментарий
  (не влияет на остаток, чисто для памяти). При сохранении остаток
  нужного варианта увеличивается — атомарно, триггером на таблице
  `stock_receipts`, которая заодно ведёт лог поступлений. Кладовщик
  видит только свои записи (полная история — `/warehouse/receiving-history`,
  только CEO).
- **Заказ** (`/warehouse/order`, только Кладовщик) — это и есть
  создание заказа, просто оформленное через складскую форму: тот же
  компонент `components/OrderForm.tsx`, что и `/orders/new` у CEO.
  В конце формы — переключатель «Забирает сейчас» / «Оставить на
  потом»: первое сразу переводит заказ в статус **«Выдан»** (товар
  физически покидает склад, остаток списывается немедленно — это
  переиспользует уже готовый триггер списания, который срабатывает при
  входе в `in_production` **или** `issued`, без отдельной логики);
  второе оставляет заказ «Новым» — запись на будущее, остаток не
  трогается, спишется позже, когда кто-то (кладовщик или CEO)
  переведёт заказ в «В производстве» или «Выдан». У CEO на
  `/orders/new` этого переключателя нет — там заказ всегда создаётся
  «Новым», как и раньше.
- **История** (`/warehouse/history`, доступен и CEO) — список заказов
  со статусом «Выдан»: дата фактической выдачи (`orders.issued_at`,
  отдельное поле от `created_at` — заказ мог полежать «Новым» и выдан
  позже) + имя клиента. Клик открывает уже существующую `/orders/[id]`
  — она и так корректно прячет цены от кладовщика, отдельную страницу
  заводить не пришлось.

И «Приход», и «Заказ» позволяют завести совершенно новый товар прямо в
процессе (только название + код, без цены — её потом выставит CEO на
«Складе»), если нужного ещё нет в каталоге.

### Быстрое добавление вариантов — сетка размер×цвет

Вместо создания вариантов по одному, в «Приходе» и в форме CEO
«Добавить вариант» на «Складе» есть режим сетки
(`components/SizeColorGrid.tsx`): вводите размеры и цвета через
запятую, дальше — вкладки по цвету со списком размеров и полем
количества у каждого (не 2D-таблица — на телефоне неудобно), заполняете
нужные ячейки и сохраняете всё одним действием. Печать — одно общее
значение на всю партию (не по ячейке), чтобы не городить трёхмерную
сетку. В «Приходе» сохранение сетки создаёт варианты и пишет для
каждого запись в лог поступлений (`stock_receipts`); на «Складе» —
сразу выставляет остаток напрямую, как обычное ручное добавление.
Сетка создаёт только новые комбинации — если вариант с таким
цветом+размером уже есть, эта попытка для него завершится ошибкой
(пополняйте его обычным способом).

## Склад: готовая продукция vs склад сырья

У товара (`products.warehouse_type`) есть тип — «Готовая продукция»
или «Склад сырья» (материалы; хранится как `'production'` в БД —
переименовано только отображаемое название, не значение), общий на
все его варианты. Существующие товары при миграции получили «Готовая
продукция». На «Складе» — переключатель сверху, фильтрующий список по
типу; список сгруппирован по названию товара (без повторов), клик
открывает карточку товара со всеми его вариантами — так остатки по
размерам/цветам видно сразу, а не вперемешку с другими товарами.
Задать тип может любая роль при создании **нового** товара; изменить
тип у **уже существующего** товара может только CEO (переключатель в
шапке карточки товара, через `product_variants_view_update` — попытка
кладовщика отклоняется на уровне БД, не только скрытием элемента
интерфейса). Поиск товара в «Заказе»/`/orders/new` показывает только
готовую продукцию — сырьё клиенту не заказывают; «Приход» показывает
и то, и другое, так как сырьё тоже приходуется.

## Автосписание склада

Списание происходит автоматически при переводе заказа в статус
**«В производстве»** (кладовщик начинает собирать заказ вручную) или
**«Выдан»** (заказ оформлен через «Заказ» с переключателем «Забирает
сейчас» — товар уже выдан). При
отмене заказа (статус «Отменён») или при его удалении товар
возвращается на склад автоматически.

Форма создания заказа только предупреждает (красным текстом), если
запрошено больше, чем есть в наличии, но **не блокирует** отправку —
заказ можно создать под будущую поставку, решение остаётся за тем, кто
собирает заказ. Настоящая гарантия от ухода остатка в минус — на
уровне базы, в момент реального списания: атомарный
`UPDATE product_variants SET stock_quantity = stock_quantity - N WHERE
stock_quantity >= N` внутри триггера на смену статуса, в одной
транзакции с самим изменением статуса. Если товара не хватает —
`UPDATE` не находит строку, триггер бросает исключение, вся транзакция
(включая смену статуса) откатывается. Та же блокировка строки в
Postgres не даёт двум кладовщикам одновременно увести один и тот же
вариант в минус — второй `UPDATE` всегда видит уже уменьшённое первым
значение.

Сумма заказа (`orders.total`) не принимается от клиента (кладовщик не
видит цены и не может её посчитать) — она автоматически пересчитывается
триггером как сумма сохранённых цен позиций (`order_items.price`,
зафиксированных на момент добавления, а не текущей цены каталога —
иначе сумма старых заказов "плавала" бы при изменении цен). Цену
позиции, которую добавляет кладовщик, сервер подставляет сам из
текущей цены товара — от кладовщика она не принимается и не может быть
подделана через прямой запрос к API.

### Известные ограничения

- Зависимость `next` обновлена до 14.2.35 (патч устраняющий критическую
  уязвимость). Несколько high-severity предупреждений `npm audit`
  остаются нерешёнными, так как фикс требует мажорного обновления до
  Next 16 — они касаются функций, которые это приложение не использует
  (middleware, i18n, `next/image` remotePatterns). Периодически
  проверяйте `npm audit` и обновляйтесь.
- Убедитесь, что DigitalOcean App Platform запускает `npm run build` +
  `npm run start` (production), а не `npm run dev` — dev-режим отдаёт
  подробные ошибки и не предназначен для публичного доступа.
- Приложение не ограничивает частоту запросов (rate limiting) на своей
  стороне — полагается на встроенные защиты Supabase Auth.

## Валюта

По умолчанию суммы форматируются в рублях (`lib/format.ts`, функция `formatMoney`). При необходимости поменяйте код валюты там же.
